# イベント参加者調整App MVP要件定義

作成日: 2026-06-01

## 1. 目的

イベント管理者がプランとイベントを作成し、招待者が配信用URLから出欠を回答できるWebアプリを提供する。

MVPでは、イベント参加者の出欠調整に必要な最小機能を優先し、管理者招待、定員制限、有効期限、外部アプリ連携などは将来拡張として扱う。

## 2. 技術スタック

- ホスティング: Vercel
- 認証: Firebase Authentication
- データベース: Firestore
- 通知: Firebase Cloud Messagingを想定
- UI: レスポンシブWebアプリ

## 3. 用語定義

| 用語 | 定義 |
| --- | --- |
| アプリ管理者 | アプリ全体の運用者。MVPでは開発者1名を想定する。 |
| イベント管理者 | 管理画面にログインし、プラン、イベント、出欠を管理する利用者。 |
| 招待者 | イベント管理者から共有された出欠入力URLにアクセスし、出欠を回答する利用者。 |
| プラン | 複数イベントをまとめる単位。年月、配信用URL、任意のアクセスコードを持つ。 |
| イベント | プラン配下の日程単位。日付、時間帯、場所、受付ステータスを持つ。 |
| 回答 | 招待者がイベントごとに登録する出欠、コメント、回答日時などの情報。 |
| PIN | 招待者本人の再編集用に使う4桁数字。プラン単位でニックネームと組み合わせて本人識別する。 |
| アクセスコード | 招待者が配信用URLにアクセスした際、プラン単位で任意に求められる閲覧用コード。イベント管理者ログインパスワードとは別物。 |

## 4. MVPスコープ

### 4.1 MVP対象

- イベント管理者ログイン
- イベント管理者ログインパスワードのリセット
- イベント管理者アカウントの手動作成
- プラン作成、一覧表示、無効化
- プラン配信用URLの発行、表示、コピー
- イベント作成、一覧表示、更新、無効化
- イベントステータス変更
- 出欠サマリー表示
- 出欠内訳表示
- イベント管理者による回答の代理追加、修正
- イベント管理者によるPINリセット
- 招待者による出欠入力、再編集
- 招待者回答時のイベント管理者向けPush通知
- スマホ優先の招待者UI
- PCでも使いやすい管理画面UI

### 4.2 MVP対象外

- アプリ管理者向けWeb管理画面
- イベント管理者の自己登録
- イベント管理者の招待URL発行
- イベント管理者の承認制
- プラン有効期限
- 定員による入力制限
- 定員到達時の通知
- 物理削除
- tennis-organizing-app連携
- 参加者情報の自動インポート、エクスポート
- URL再発行
- 招待者向けメール、LINE等の自動送信

## 5. 共通方針

- Webアプリはレスポンシブ対応とする。
- UIはサークル向けのカジュアルアプリではなく、運営者が出欠状況を効率よく確認、集計するためのビジネスアプリ寄りにする。
- 招待者側はスマホ利用を主想定とし、スマホ優先UIにする。
- 管理画面はPC利用を主想定とし、マイプラン、イベント一覧、出欠内訳をテーブル中心で構成する。
- 管理画面はスマホでも崩れることなく閲覧、操作できるようにする。
- 全体のデザインは白、グレーをベースに、アクセントカラーを1色だけ使う落ち着いた業務アプリ風にする。
- 派手な装飾、SNS風、ゲーム風、ポップすぎる表現は避ける。
- 削除操作は物理削除ではなく無効化として扱う。
- 無効化済みデータは通常利用画面では非表示または操作不可にする。
- 作成日時、更新日時を主要データに保持する。
- 実装中にMVP判断へ影響する不明点が出た場合は、仕様を仮決めせず確認する。

## 6. 利用者と権限

| 役割 | 人数 | 操作場所 | 権限 |
| --- | ---: | --- | --- |
| アプリ管理者 | 1名 | Firebase Console | イベント管理者アカウントの手動作成、無効化。技術的には全データへアクセス可能。 |
| イベント管理者 | 複数名 | Web管理画面 | 自分が作成したプラン、イベント、出欠情報のみ閲覧、編集可能。 |
| 招待者 | 複数名 | 出欠入力URL | 自分の回答のみ入力、再編集可能。他招待者の回答は閲覧不可。 |

### 6.1 アプリ管理者

- MVPでは開発者がアプリ管理者を担当する。
- アプリ管理者向けのWeb管理画面は提供しない。
- アプリ管理者はFirebase Consoleでイベント管理者アカウントを手動作成する。
- アプリ管理者はFirebase Console上では全データにアクセス可能だが、通常業務として出欠データの操作は行わない。

### 6.2 イベント管理者

- Firebase Authenticationで作成されたアカウントでログインする。
- イベント管理者アカウントはアプリ管理者が手動作成する。
- イベント管理者は複数名登録できる。
- MVPではイベント管理者ごとにデータを分離する。
- イベント管理者は、自分が作成したプラン、イベント、出欠情報のみ閲覧、編集できる。
- 他のイベント管理者が作成したデータは閲覧、編集できない。

### 6.3 招待者

- Firebase Authenticationのログインは不要とする。
- イベント管理者から共有された配信用URLにアクセスする。
- アクセスコードが設定されている場合は、アクセスコード入力後に出欠入力へ進む。
- ニックネームとPINで本人識別する。
- 他の招待者の情報は表示しない。

## 7. 認証・本人識別

### 7.1 イベント管理者認証

- Firebase Authenticationのメールアドレス、パスワード認証を使用する。
- イベント管理者の自己登録画面は提供しない。
- イベント管理者アカウントの初回作成は、アプリ管理者がFirebase Consoleで手動作成する。
- イベント管理者ログインパスワードを忘れた場合は、イベント管理者自身がログイン画面からパスワードリセットを実行できる。
- パスワードリセットはFirebase Authenticationのメール送信機能を使用する。
- アプリ管理者は通常運用としてイベント管理者ログインパスワードを代理確認、代理通知しない。

### 7.2 招待者本人識別

- 招待者はプラン単位でニックネームとPINを登録する。
- PINは4桁数字文字列とする。
- `0000` から `9999` まで許可する。
- PINは数値ではなく文字列として扱い、先頭0を保持する。
- 同一プラン内で、同じニックネームと同じPINの場合は同一招待者として扱う。
- 同一プラン内で、同じニックネームかつ別PINの場合はエラーにする。
- 別ニックネームで同じPINは許可する。
- ニックネームは表示用の `nickname` と重複判定用の `nicknameKey` を分けて保持する。
- 表示用の `nickname` は、入力値の前後空白のみ除去して保存する。
- 重複判定用の `nicknameKey` は、前後空白除去、全角英数字の半角化、英字小文字化、連続空白の単一化を行う。
- ひらがな/カタカナ変換、漢字表記ゆれの吸収はMVP対象外とする。

### 7.3 PINリセット

- 管理画面にPINは表示しない。
- PINを忘れた招待者は、イベント管理者へLINE等でリセットを依頼する。
- 本人確認はシステム化せず、イベント管理者の運用でカバーする。
- イベント管理者は管理画面から対象招待者のPINをリセットできる。
- 新PINはイベント管理者がLINE等で招待者へ連絡する。
- PINリセット後、旧PINでは再編集できない。
- PINリセットでは既存の出欠回答を維持する。
- PINリセットのみでは回答日時を更新しない。
- PINリセット日時、操作したイベント管理者を監査情報として記録する。
- PINはFirestoreに平文保存せず、ハッシュ化して保持する。

## 8. プラン管理

### 8.1 マイプラン

- イベント管理者は自分が作成した有効なプランのみ一覧表示できる。
- 並び順は追加順とする。
- 有効なプランは最大3件まで同時に作成できる。
- 削除済みプランは3件上限に含めない。
- プランが3件ある場合、プラン追加操作は不可とし、理由を表示する。

### 8.2 プラン追加

プラン追加時に以下を登録する。

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| プラン名 | 必須 | 管理画面、招待者画面、通知で表示する名称。 |
| 年月 | 必須 | 対象年月。年月選択UIで入力する。 |
| アクセスコード | 任意 | 設定時のみ、招待者アクセス時に入力を求める。6〜12桁の数字。 |

- アクセスコードは `設定しない` / `設定する` をラジオボタンで選択する。
- `設定する` を選択した場合のみ、アクセスコード入力を必須にする。

作成時に以下を自動生成する。

- プランID
- ownerUid
- 出欠入力用の配信用URL token
- 作成日時
- 更新日時
- 有効状態

### 8.3 プラン更新

- イベント管理者は自分が作成したプランのプラン名、年月、アクセスコードを更新できる。
- アクセスコードは設定、変更、解除できる。
- アクセスコード設定済みの場合、編集画面では `現在のアクセスコードを維持する`、`アクセスコードを解除する`、`別のアクセスコードを設定する` から選択する。
- アクセスコード未設定の場合、編集画面では `アクセスコードを設定しない`、`アクセスコードを設定する` から選択する。
- `アクセスコードを設定する` または `別のアクセスコードを設定する` を選択した場合のみ、6〜12桁の数字入力を必須にする。
- アクセスコードを変更または解除した場合、招待者への周知はイベント管理者がLINE等の運用で対応する。
- アクセスコード変更時に、システムから招待者へ自動通知しない。
- プラン編集画面で保存した場合は、マイプランへ戻る。
- プラン編集画面でキャンセルした場合は、マイプランへ戻る。

### 8.4 配信用URL

- プランごとに出欠入力用の配信用URLを作成する。
- 配信用URLはイベント管理者が手動で招待者へ共有する。
- システムから招待者へ自動送信しない。
- URLには推測困難なランダムtokenを使用する。
- 例: `/invite/{publicToken}`
- 管理画面ではURL表示とコピーボタンを提供する。
- MVPではURL再発行は対象外とする。

### 8.5 プラン削除

- プラン削除は画面上 `削除` と表示し、内部的には無効化として扱う。
- 削除時は確認ダイアログを表示し、招待URLからアクセスできなくなることを明示する。
- 無効化済みプランの配信用URLへアクセスした場合、出欠入力フォームは表示せずエラーを表示する。
- 無効化済みプランはイベント管理者の通常一覧に表示しない。
- 物理削除は行わない。

## 9. イベント管理

### 9.1 イベント一覧

- イベントはプラン配下に作成する。
- 並び順は日程昇順とする。
- 同一日程の場合は、時間帯順、登録順の順に表示する。
- イベントごとに出欠サマリーを表示する。
- 出欠サマリーは `○`、`△`、`×` の人数を表示する。
- イベント一覧では `イベント` 列を一番左に表示する。
- イベント一覧の出欠内訳導線は、画面上 `出欠内訳` と表示する。
- イベント一覧のステータス変更は `受付中` / `締切済` の2択セグメントで表示する。
- イベント一覧でステータスを変更する場合は、確認ダイアログを表示する。

### 9.2 イベント追加

イベント追加時に以下を登録する。

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| イベント名 | 任意 | 未入力可。 |
| 日程 | 必須 | カレンダーから選択する。 |
| 時間帯 | 必須 | AMまたはPMを選択する。 |
| 場所 | 必須 | テキスト入力。 |

- イベント追加画面のイベント名には、初期値としてプラン名を表示する。
- 初期値はイベント管理者が変更または削除できる。

作成時に以下を自動設定する。

- イベントID
- プランID
- 登録順
- ステータス: 受付中
- 有効状態
- 作成日時
- 更新日時

### 9.3 イベント更新

- イベント管理者はイベント名、日程、時間帯、場所を更新できる。
- イベント管理者はイベントステータスを `受付中`、`締切済` に変更できる。
- 締切済イベントは招待者による出欠変更を不可にする。
- イベント管理者による回答修正は締切済でも可能とする。
- イベント編集画面で保存した場合は、イベント一覧へ戻る。
- イベント編集画面でキャンセルした場合は、イベント一覧へ戻る。

### 9.4 イベント削除

- イベント削除は画面上 `削除` と表示し、内部的には無効化として扱う。
- 削除時は確認ダイアログを表示し、招待者画面には表示されなくなることを明示する。
- 無効化済みイベントは招待者画面には表示しない。
- 無効化済みイベントの既存回答は保持する。
- 無効化済みイベントはイベント管理者の通常一覧に表示しない。

## 10. 出欠管理

### 10.1 出欠値

出欠は以下の3値とする。

| 値 | 意味 |
| --- | --- |
| ○ | 参加 |
| △ | 未定、条件付き参加 |
| × | 不参加 |

### 10.2 出欠内訳一覧

イベント管理者はイベントごとに招待者の回答一覧を確認できる。
イベント情報エリアには `プラン`、`日程`、`時間帯`、`場所`、`状態` を1行で表示する。

表示項目は以下とする。

- ニックネーム
- 出欠
- コメント
- 回答日時
- 最終更新者

PINは表示しない。

### 10.3 回答の代理追加

- イベント管理者は招待者の回答を代理追加できる。
- 代理回答は出欠内訳パネル右上の `代理回答` ボタンから入力ポップアップを開いて行う。
- 代理追加時もニックネームとPINを設定する。
- 代理追加された招待者は、同じニックネームとPINで後から再編集できる。
- 代理追加時の最終更新者は `管理者(Admin)` とする。

### 10.4 回答の修正

- イベント管理者は既存回答を修正できる。
- 回答修正は出欠内訳の対象行にある `修正` ボタンから修正用ポップアップを開いて行う。
- イベント管理者が修正した場合も回答日時を更新する。
- イベント管理者が修正した場合、最終更新者は `管理者(Admin)` とする。
- 招待者が修正した場合、最終更新者は `招待者(Guest)` とする。

## 11. 招待者向け出欠入力

### 11.1 アクセス

- 招待者はイベント管理者から共有された配信用URLを開く。
- プランが無効化されている場合はエラーを表示する。
- publicTokenが不正な場合はエラーを表示する。
- アクセスコードが設定されている場合は、アクセスコード入力を求める。
- アクセスコード認証後、ニックネームとPINを入力する。

### 11.2 初回入力

- 同一プラン内に同じニックネームが存在しない場合、新しい招待者として登録する。
- 出欠入力画面では、プラン内の有効な受付中イベントを表示する。
- 締切済かつ招待者本人の回答が存在しないイベントは表示しない。
- イベントごとにステータスを表示する。
- 受付中イベントでは、出欠とコメントを入力できる。
- 締切済イベントでは、出欠とコメントを編集できない。
- 他の招待者の回答は表示しない。

### 11.3 再編集

- 再編集時も、同じURLからアクセスする。
- 同じニックネームとPINを入力すると、既存の自分の回答を読み込む。
- 同じニックネームでPINが異なる場合はエラーにする。
- 受付中イベントのみ変更できる。
- 締切済イベントは、自分の既存回答がある場合のみ表示し、表示のみとする。

### 11.4 保存

- 保存ボタン押下で回答を確定する。
- 保存時にサーバー側でプラン有効状態、イベント有効状態、イベントステータスを再検証する。
- 保存直前にプランが無効化された場合は保存失敗とする。
- 保存直前にイベントが締切済へ変更された場合、そのイベントの更新は失敗とする。
- 保存成功後、出欠入力完了画面へ遷移する。

## 12. 出欠入力完了画面

保存成功後、以下のメッセージを表示する。

```text
出欠入力が完了しました。
再編集する場合、初回入力時と同じニックネーム、PINで共有URLから再度アクセスしてください。
締切後に出欠を変更する場合、画面から変更できませんので管理者に直接ご連絡ください。
```

加えて、保存した入力内容を表示する。

## 13. Push通知

### 13.1 通知条件

- 招待者が回答を追加または更新した場合、対象プランのイベント管理者へPush通知する。
- イベント管理者による代理追加、修正、PINリセットでは通知しない。
- 通知はスマホ、PWA等で通知許可されている場合のみ送信される。
- 通知不可端末、通知拒否、送信失敗の場合も、回答保存自体は成功とする。

### 13.2 通知許可UI

- イベント管理者の初回ログイン直後に、ブラウザ通知許可ダイアログを自動表示する。
- ブラウザ側で自動表示が抑制された場合、または後から許可したい場合は、マイプランの「通知を有効にする」から通知有効化できる。
- 通知許可済みの場合は、通知設定済みであることを表示する。
- 通知拒否済みの場合は、ブラウザまたは端末設定から通知を許可する必要があることを表示する。
- VAPIDキー未設定、通知非対応ブラウザ、通知拒否済みの場合も管理画面の表示と回答保存は継続できる。

通知有効化UIの案内文言は以下とする。

```text
招待者の回答更新を通知で受け取れます。
```

ボタン文言は以下とする。

```text
通知を有効にする
```

### 13.3 通知内容

通知に表示する文言は以下とする。

```text
プラン△△△を○○〇さんが更新しました。
```

- `△△△`: プラン名
- `○○〇`: 招待者のニックネーム

### 13.4 通知タップ時の遷移

- 通知をタップすると、対象プランのイベント一覧に遷移する。
- 未ログインの場合はログイン画面を経由し、ログイン後に対象プランへ遷移する。

## 14. データ設計方針

MVPでは、将来の拡張とFirestore Security Rulesの制御を考慮し、以下の単位でデータを分ける。

```text
eventAdmins
plans
events
guests
responses
notificationTokens
auditLogs
```

### 14.1 plans

主な項目:

- planId
- ownerUid
- name
- yearMonth
- passwordHash
- publicToken
- isActive
- createdAt
- updatedAt

### 14.2 events

主な項目:

- eventId
- planId
- ownerUid
- name
- eventDate
- timeSlot: AM / PM
- place
- status: accepting / closed
- sortOrder
- isActive
- createdAt
- updatedAt

### 14.3 guests

主な項目:

- guestId
- planId
- ownerUid
- nickname
- nicknameKey
- pinHash

## 15. セキュリティ要件

- イベント管理者は `ownerUid` が自分のUIDと一致するデータのみ閲覧、編集できる。
- 招待者向けAPIまたはFirestoreアクセスでは、他招待者の回答、コメント、PIN関連情報を返さない。
- PINは平文保存しない。
- アクセスコードは平文保存しない。
- publicTokenは推測困難な値にする。
- 招待者による保存時は、クライアント表示状態を信用せず、サーバー側で状態を再検証する。
- 無効化済みプラン、無効化済みイベント、締切済イベントへの不正更新を防ぐ。

## 16. UI要件

### 16.1 招待者画面

- スマホ優先で設計する。
- ニックネーム+PIN入力後、各イベントに対して `〇`、`△`、`×` のSVGアイコンのみを大きめのボタンで選択できる1カラムUIにする。
- 片手操作しやすいフォーム配置にする。
- 出欠選択はイベントごとに分かりやすく表示する。
- 締切済イベントは編集不可であることを明確にする。
- 保存中、保存成功、保存失敗の状態を表示する。
- 入力エラーは該当項目の近くに表示する。

### 16.2 管理画面

- PC利用を主想定とし、一覧確認、集計確認、詳細確認を効率よく行える構成にする。
- マイプラン、イベント一覧、出欠内訳はテーブル中心で構成する。
- `○`、`△`、`×` の人数はカードまたはバッジで一目で分かるように表示する。
- スマホでもレイアウトが崩れず、閲覧、操作できるようにする。
- マイプラン、イベント一覧、出欠内訳の階層が分かる画面構成にする。
- URLコピー成功はボタン付近に `コピーしました` を短時間表示し、URLコピー失敗は画面内エラーとして表示する。
- 削除操作、PINリセット操作、回答修正操作は誤操作を防ぐ確認UIを設ける。

## 17. 状態遷移

### 17.1 プラン

```text
有効 -> 無効
```

- MVPでは再有効化は必須機能としない。
- 再有効化を実装する場合も物理削除は行わない。

### 17.2 イベント

```text
受付中 -> 締切済
締切済 -> 受付中
有効 -> 無効
```

- ステータス変更はイベント管理者のみ可能。
- 無効化済みイベントは招待者画面に表示しない。

### 17.3 招待者回答

```text
未回答 -> 回答済
回答済 -> 再編集済
回答済 -> 管理者修正済
```

- 招待者は受付中イベントのみ編集可能。
- イベント管理者は締切済イベントの回答も修正可能。

## 18. まず防ぐべき不具合

| 優先度 | 不具合 | 理由 |
| --- | --- | --- |
| 致命 | 招待者画面で他人の回答やPIN関連情報が見える | 個人情報、本人識別情報の漏洩につながる。 |
| 致命 | 無効化済みプランに回答できる | 管理者が停止した募集が継続してしまう。 |
| 重大 | 締切済イベントを招待者が更新できる | 締切運用が成立しない。 |
| 重大 | 同じニックネームで別PINの登録を許す | 本人識別が壊れる。 |
| 重大 | イベント管理者Aがイベント管理者Bのデータを閲覧、編集できる | データ分離要件に反する。 |
| 重大 | プラン3件制限を同時操作で超える | MVP制約が守れない。 |
| 軽微 | Push通知が届かない | 回答保存自体は成立するため、補助機能として扱う。 |

## 20. テストケース分類

### 20.1 正常系

- イベント管理者がログインし、プランを作成できる。
- イベント管理者がログインパスワードリセットメールを送信できる。
- イベント管理者がプランにイベントを追加できる。
- イベント管理者がアクセスコードを変更、解除できる。
- 招待者がURLから初回回答できる。
- 招待者が同じニックネームとPINで再編集できる。
- イベント管理者が出欠サマリーと内訳を確認できる。
- イベント管理者がPINをリセットし、招待者が新PINで再編集できる。

### 20.2 異常系

- 不正なpublicTokenでアクセスした場合、エラー表示になる。
- 無効化済みプランのURLにアクセスした場合、エラー表示になる。
- 同じニックネームで別PINを入力した場合、エラー表示になる。
- 締切済イベントを招待者が保存しようとした場合、保存できない。
- 他イベント管理者のデータを取得しようとした場合、拒否される。

### 20.3 境界値

- プランが3件の状態で4件目を作成できない。
- 無効化済みプランがある場合、プラン3件制限に含まれない。
- PIN `0000` を登録、照合できる。
- PIN `9999` を登録、照合できる。
- イベント名未入力でもイベントを作成できる。

### 20.4 状態遷移

- 受付中イベントを締切済に変更すると、招待者が編集できなくなる。
- 締切済イベントを受付中に戻すと、招待者が編集できる。
- プランを無効化すると、配信用URLから入力できなくなる。
- PINリセット後、旧PINでは再編集できず、新PINでは再編集できる。

### 20.5 通し実行・依存関係

- プラン作成から招待者回答、管理者確認、PINリセット、再編集まで通しで検証する。
- 単体では成功しても、複数イベント、複数招待者、複数イベント管理者でデータ分離が崩れないことを確認する。
- テスト実行順序に依存しないよう、状態初期化とテストデータ準備を明示する。
- 同一実機に対して自動化スクリプトを並列実行しない。

## 21. 将来拡張

### 21.1 tennis-organizing-app連携

MVPでは対象外とする。

将来的には、RSVP側のイベント出席者をtennis-organizing-app側で選択済み参加者として表示することを想定する。

- 連携対象の詳細は別途調整する。
- 参加者名はニックネームのみを想定する。
- RSVP側では将来連携しやすいよう、guestId、nickname、eventId、attendanceStatusを構造化して保持する。
- 連携時に `○` のみを対象とするか、`○ + △` を対象とするかは将来検討とする。

### 21.2 管理チーム

MVPではイベント管理者ごとにデータを分離する。

将来的に複数イベント管理者で同じプランを共同管理する場合は、全管理者共有ではなく、管理チーム単位の共有を検討する。

管理チーム機能で想定する内容:

- 複数のイベント管理者を同じ管理チームに所属させる。
- チーム単位でプラン、イベント、出欠回答を所有する。
- 同じチームのイベント管理者だけが、チーム配下のデータを閲覧、編集できる。
- チームメンバーの追加、削除により管理権限を調整する。
- チーム内の別イベント管理者が、PINリセットや回答修正を代理実行できる。

MVPでは個人単位の `ownerUid` でデータを分離し、管理チーム導入時に `teamId` などの共有単位を追加する想定とする。

### 21.3 管理者招待

MVPではイベント管理者アカウントをFirebase Consoleで手動作成する。

将来的に運用負荷が増えた場合は、以下を検討する。

- イベント管理者招待URL
- イベント管理者自己登録
- アプリ管理者による承認制
